# tests/

Тесты UI-системы: `unit/` (Vitest, чистая логика), `e2e/` (Playwright, компонентные страницы), `a11y/` (axe-сценарии), `visual/` (скриншот-эталоны).

## Граница unit (Vitest) vs e2e (Playwright) — конвенция (T1.6, 06 §9)

**Чистая логика — отдельно от DOM-кода.** DOM-независимая логика модулей (парсинг localStorage, расчёт валидности, VI-состояния, синхронизация select) выносится в чистые функции и тестируется юнит-тестами — быстрыми, детерминированными, без браузера. Guard'ы и лёгкие DOM-проверки (готовность документа, отсутствие элементов) — тоже юнит-уровень: jsdom достаточен.

**DOM-поведение — только Playwright** (`tests/e2e/`, харнесс — T1.4): фокус, клавиатура, поведение компонентов на стендах `showcase/pages/`, axe. Если сценарий можно выразить вызовом функции — он не должен жить в e2e.

Практика:

- юнит-тесты живут ТОЛЬКО в `tests/unit/*.test.js` (глоб `vitest.config.mjs`, `npm run test:unit`); Playwright-конфиг (T1.4) обязан ограничить свой testDir каталогом `tests/e2e/` — его дефолтный testMatch цепляет `*.test.js` по всему репозиторию;
- изоляция: скриптовые модули (IIFE по образцу `docs/templates/module-template.js`) тестируются в собственной песочнице `new JSDOM(...)` на каждый тест — эталон: `tests/unit/module-template.test.js`;
- coverage-пороги не вводятся до появления реальной логики (T5.5, T7.3, T9.1).

Харнесс e2e подключается в T1.4 — до тех пор e2e/a11y/visual-сценарии фиксируются текстом в README стендов.

- Можно: сценарии, привязанные к стендам `showcase/pages/`; эталонный тест контракта `docs/templates/module-template.js`.
- Нельзя: тесты, не привязанные к каноническому HTML компонента; DOM-поведение в юнит-тестах.
