# MVP, риски и финальные рекомендации

## 1. MVP (MoSCoW)

### Must have (первая production-версия = фазы 1–4 roadmap)

- Токены (2 слоя) + тема-референс + стенд токенов, контраст AA проверен;
- base: reset, шрифты Golos, focus-политика, skip-link, типографика rem, container/grid;
- Компоненты: button, link, tag/badge, card, breadcrumbs (+schema.org), image-паттерн, alert, empty/error-паттерны;
- Формы: все нативные контролы + form-grid + состояния ошибок (клиентские и серверные) + JS-валидация как PE;
- VI-модуль ГОСТ Р 52872;
- Showcase с доками компонентов и quickstart;
- CI: lint + unit + e2e + axe + visual (PR-гейты);
- Интеграция на один пилотный сайт (стенд минимум): подключение + 2–3 страницы, включая форму;
- Дистрибутив: dist + версионированная папка + README по подключению.

### Should have (сразу после MVP — фазы 5–6)

- Modal, dropdown, tabs, accordion, custom select, pagination, table, loader;
- Страничные паттерны (list/detail/form/landing);
- Второй пилотный сайт (другая структура страниц, тот же бренд);
- forced-colors, ручной скринридер-протокол;
- Release pipeline с матричной nightly.

### Could have (отложено осознанно)

- Tooltip, carousel, skeleton, toasts, stepper;
- PHP-хелперы рендера;
- codemod-скрипты миграций;
- Storybook (пересмотр при росте команды);
- Общий статик-домен ассетов группы.

### Don't do (в MVP сознательно не делаем)

- **Vue/React/web-components runtime** — нарушает ключевое ограничение «нативный HTML/CSS + минимум JS»;
- **CSS-in-JS, Tailwind, Bootstrap, препроцессоры** — обоснование в architecture §2;
- **Свой конструктор форм/«Bitrix-модуль с настройками в админке»** — это отдельный продукт с другой командой поддержки; MVP — библиотека вёрстки и поведения;
- **Иконочный фреймворк (икон-шрифты, спрайт-менеджер)** — inline SVG по правилам image-паттерна; система поставляет только общие UI-иконки (chevron, close, search, arrow);
- **Полная матрица IE/старых браузеров** — целевые браузеры evergreen (два последних мажорных); фиксация в Phase 0;
- **Автоматическое тестирование на реальных сайтах из репо системы** — граница ответственности сайтов;
- **Тёмная тема** — не требуется ни одним требованием; `prefers-color-scheme` не закладываем в токены заранее (расширение — minor-версией, механизм тем это позволяет).

## 2. Архитектурные риски и митигации

| # | Риск | Класс | Митигация |
|---|---|---|---|
| 1 | Конфликт с legacy-CSS сайтов (глобальные стили тегов, каскад старых шаблонов) | Bitrix/legacy | namespace `ui-` + односелекторная специфичность; подключение до CSS сайта; селекторы компонентов всегда класс-на-класс (побеждают tag-стили legacy); журнал конфликтов пилотов → известные ограничения в доке |
| 2 | Legacy `!important` в старых шаблонах побеждает систему | legacy-CSS | «не боремся важностью с важностью»: ui-компоненты не поднимают специфичность; конфликтная страница либо изолируется (`@scope`-подобная обёртка/новая страница), либо остаётся на старом UI; правило: система не встраивается внутрь агрессивных legacy-виджетов |
| 3 | Расползание токенов и over-abstraction (сотни переменных, которые никто не переопределяет) | abstraction | жёсткое правило: слой 3 только при потребности 2+ сайтов; ревью-гейт на новые токены; периодический аудит неиспользуемых токенов |
| 4 | Over-engineering JS (микрофреймворк «на всякий случай») | abstraction | правило «сначала нативно, JS только там, где нативного нет»; каждый JS-модуль в backlog обязан иметь строку «что без него происходит» |
| 5 | Захардкоженные визуальные значения мимо токенов (деградация дисциплины через год) | maintenance | stylelint declaration-strict-value (hex только в tokens) как mandatory-гейт — правило исполняется машиной, не ревью |
| 6 | Версионный дрейф сайтов (A на 1.2, B на 1.7, C требует 2.0) | versioning | политика N−1 с окном 6 месяцев; major-версии в отдельных папках; deprecation-анонсы в minor; upgrade-гайд с чек-листом ≤ 0.5 дня |
| 7 | Breaking change в HTML-паттерне ломает прод сайтов, где разметку копировали | versioning/adoption | правило «API компонента = классы и HTML»; изменения канонического HTML — только major; канонические паттерны тестируются html-validate на дрейф |
| 8 | Саботаж/непринятие интеграторами («проще сверстать свою кнопку») | adoption | дока «для Bitrix-разработчика за 30 минут»; копипаст-паттерны без сборки; сниппеты header.php; incognito-тест на реальном интеграторе; quick win'ы — формы и VI (боль сайтов именно там) |
| 9 | VI-перекраска `!important` ломается на нестандартных страницах сайта | a11y | контракт: компоненты не используют inline-стили и нестандартные цвета (lint); инструкция для сайтов «как проверять страницы в VI»; VI-сценарий в релизном чек-листе |
| 10 | Контраст/доступность регрессируют между релизами | a11y | axe в PR-гейте на каждом стенде и состоянии; контраст-пары токенов — частью tokens-стенда; ручной скринридер-протокол в релизный чек-лист |
| 11 | Шрифтовая нагрузка (Golos 3 веса × cyr/lat на каждом сайте) | performance | unicode-range-сплиты + preload только 400/500 cyr (паттерн career-portal); `font-display: swap`; аудит веса в релизе |
| 12 | Поддержка малой командой (1–2 человека) при росте числа компонентов | maintenance | скучный стек (нативный CSS/JS, минимум dev-зависимостей); всё enforcing'ится CI; компонентная папка самодостаточна (ревью без контекста всей системы); P2-очередь — только по потребности реальных сайтов |
| 13 | Потеря актуальности документации | maintenance | дока живёт рядом с компонентом (README в папке) и рендерится в showcase из тех же источников; инкогнито-тест как гейт релиза |
| 14 | Зависимость от toolchain-версий (Node-инструменты гниют за 2–3 года) | dependencies | минимум dev-зависимостей (esbuild, stylelint, eslint, playwright, vitest, html-validate); точечные обновления в CI-расписании; dist собираем на каждой сборке (нет «забытых» локальных артефактов) |
| 15 | Мажорная миграция 2.0 окажется неподъёмной для сайтов | versioning | сначала испытать процесс на minor (TASK-272); миграционные гайды с первого релиза; алиасы классов на переходный период (deprecated-класс = alias) |

### Решения Phase 0 (зафиксировано 2026-10-05)

1. **Темизация — один бренд Интер РАО.** Все сайты в корпоративной палитре. Механизм тем (`data-ui-theme` + `themes/`) остаётся в архитектуре как задел и проверяется одной синтетической тестовой темой; мульти-брендовые темы не строятся, контраст-тест — по дефолтной палитре.
2. **Дистрибуция — копия на сайт** `/local/ui/{version}/`. Общий статик-домен — отложенная опция для 5+ сайтов (файлы dist при этом не меняются, меняется только URL в сниппете).
3. **Репозиторий — GitHub**, как career-portal: Actions для CI, Pages для showcase. Перенос в корп. GitLab позже возможен без изменения структуры — пайплайны зеркалируемы.
4. **Матрица браузеров — два последних мажорных evergreen** (Chrome/Edge, Firefox, Safari: текущий + предыдущий). Технологический бюджет подтверждён: `<dialog>`, `:focus-visible`, `color-mix`, `:has()` доступны. Legacy-требований нет; при появлении — пересмотр SPIKE-230.

**Остался открытым:** выбор двух пилотных сайтов (нужен к Phase 9, желательно к концу Phase 4) — решение за менеджером. Рекомендованные критерии: первый — Bitrix-версия career-portal (вёрстка уже на компонентах-предках, самый дешёвый win), второй — корпоративный сайт группы с другой структурой страниц (доказательство переиспользования в рамках одного бренда).

## 3. Финальные рекомендации (краткие ответы)

1. **Архитектура**: единый репозиторий irao-ui; слои tokens → base → components → a11y(VI) → patterns; исходники = читаемый CSS/JS, сборка только конкатенация+минификация; ноль runtime-зависимостей; распространение версионируемыми dist-папками на сайты.
2. **CSS-подход**: собственный нативный CSS на custom properties (отказ от Bootstrap/Tailwind/CSS Modules — сравнение в architecture §2); без препроцессоров; без `@layer` для изоляции.
3. **Методология**: БЭМ с namespace `ui-` (`ui-button__icon--primary`-стиль), специфичность одного класса, состояния `is-*`, JS-хуки только через `data-ui-*`.
4. **Токены**: два слоя (примитивы/семантика) + опциональные компонентные; все `--ui-*`; тема = файл переопределения семантики под `data-ui-theme`; типографика в rem; брейкпоинты — константы, не переменные.
5. **Компоненты**: ~25 в P0/P1; карта и приоритеты в architecture §4; интерактивные — по WAI-ARIA APG с нативной деградацией; «паттерны» (header, страницы) отдельно от «компонентов» (в dist).
6. **Подключение к Bitrix**: `/local/ui/{semver}/` на сайте; 3–4 строки в `header.php` (Asset::addCss/addJs) + preload шрифтов; компоненты — копипаст HTML-паттернов; данные для JS через `<script type="application/json">`; правки в `/local/ui/` запрещены.
7. **Документация**: статический showcase-сайт (единый источник для доки, тестов и visual-регрессии) по единому шаблону страницы компонента; Storybook отложен.
8. **Тестирование**: stylelint (БЭМ+hex-гейт) + eslint + html-validate + Vitest (логика) + Playwright (e2e + axe + скриншоты) на стендах; ручной design-QA и скринридер-протокол в релизе; ничего сверх этого.
9. **Версионирование**: строгий semver, тег → dist-zip → Release; N−1 поддержка 6 месяцев; major = отдельная папка; deprecated-алиасы на переходный период; API-стабильность HTML-паттернов важнее удобства кода.
10. **Взять из career-portal (класс A)**: нативный стек без зависимостей; БЭМ+папка-блок; VI-модуль целиком; паттерн шрифтов; reset-приёмы; аккордеон grid-rows; архитектуру select-усиления; паттерны JS-модулей; идею HTML-тестов и дисциплину design-qa.
11. **Изменить относительно career-portal**: namespace `ui-` и токены `--ui-*` в 2 слоя; mobile-first вместо desktop-first; единые focus-visible/skip-link/dialog-семантика; токенизация брейкпоинтов/теней/z-index/отступов; rem-типографика; убрать site-специфику из общих модулей (dd, build.py); добавить линтеры/CI-гейты, которых не было.
12. **С чего начать**: Phase 0 (утверждение этих доков + выбор пилотов и 5 открытых вопросов) → Phase 1 (репо+конвейер) → Phase 2 (токены). Первый код — перенос `variables.css`→два слоя и `base.css`+`vi` из career-portal: это самые дешёвые шаги с наибольшей доказанной ценностью.
