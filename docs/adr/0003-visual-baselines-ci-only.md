# ADR-0003: Visual-эталоны создаёт и обновляет только CI

- **Дата:** 2026-10-05
- **Статус:** заменено [ADR-0004](0004-visual-baselines-container.md) в тот же день — CI-only подход признан тяжёлым для команды 1–2 человек; текст ниже сохранён как история решения
- **Влияет на:** [02-architecture.md](../02-architecture.md) §9; задачи T1.4, T1.5

## Контекст

Скриншот-эталоны Playwright чувствительны к растеризации шрифтов, которая различается между ОС (Windows у разработчиков локально, Linux у CI-раннеров GitHub Actions). Если эталоны создаёт разработчик локально, CI стабильно красный из-за ложных диффов; если эталоны создаёт CI — они «красные» у разработчика. Гейт, который врёт в любую сторону, теряет доверие команды за неделю и отключается — visual-регрессия перестаёт существовать.

## Решение

1. Эталоны (`toHaveScreenshot`) создаются и обновляются **исключительно CI-раннером** (Linux).
2. В репозитории настраивается джоба «Update snapshots» (workflow_dispatch): она прогоняет тесты с `--update-snapshots` и коммитит эталоны от имени бота.
3. Прямые коммиты в каталог эталонов (`tests/**/__screenshots__/`) блокируются path-защитой + CODEOWNERS — эталоны в main попадают только от бота.
4. Локальный запуск с `--update-snapshots` допустим только для отладки; несённые вручную эталоны отклоняются (п. 3).
5. Документируется правило в README тестов (T1.4): «изменил дизайн осознанно — запусти джобу обновления эталонов, приложи её ссылку в PR».

## Последствия

**Плюсы:** стабильный, заслуживающий доверия гейт; одинаковая среда создания и проверки эталонов.

**Цена/минусы:** обновление эталонов при осознанном изменении дизайна — через джобу (не мгновенно, ~минуты); требуется выделенный Linux-раннер (стандартный GitHub-hosted подходит); CI остаётся единственным местом «истины» по эталонам. Альтернатива для строгой детерминированности — Docker-раннер и локально (вводится позже без изменения этого решения).

## Проверка

T1.5: workflow path-защиты включён; контрольный PR с вручную изменённым эталоном блокируется.
