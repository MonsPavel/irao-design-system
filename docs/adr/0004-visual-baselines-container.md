# ADR-0004: Visual-эталоны — контейнер-паритет + advisory-гейт до v1.0

- **Дата:** 2026-10-05
- **Статус:** принято (заменяет [ADR-0003](0003-visual-baselines-ci-only.md))
- **Влияет на:** [02-architecture.md](../02-architecture.md) §9, §10; задачи T1.4, T1.5; iteration-план (07, Iteration 10)

## Контекст

ADR-0003 решил проблему ложных диффов (разная растеризация шрифтов Windows/Linux) через CI-only создание эталонов, но при разборе с командой цена признана высокой для состава 1–2 разработчика:

- цикл «красный PR → джоба → бот-коммит → подтянуть → ребейз» на каждое осознанное изменение;
- церемонии path-защиты + CODEOWNERS — управление уровня большой команды;
- фрикшен концентрируется в итерациях 3–8, когда эталоны создаются массово (каждый новый компонент × 3 вьюпорта);
- конфликты бинарных эталонов при параллельных PR не решаются вовсе.

## Решение

**Ось 1 — происхождение эталонов: единое контейнерное окружение.**

1. e2e/visual-тесты выполняются везде — и в CI, и локально — в одном официальном образе `mcr.microsoft.com/playwright:vX-jammy` (версия пиннится в репо рядом с версией Playwright).
2. Локально: `npm run test:docker` (docker или podman; на Windows — через WSL2). Эталоны, созданные локально в контейнере, бинарно совпадают с CI — коммитятся свободно, обычным коммитом разработчика.
3. CI-джоба `update-snapshots` (workflow_dispatch, коммит от бота) остаётся как **fallback** для машин, где контейнер недоступен.
4. Path-защита каталога эталонов и CODEOWNERS **не вводятся**, пока команда 1–2 человека. Триггер введения — рост команды или «мусорные» эталоны в PR.
5. Лицензионная оговорка: Docker Desktop в крупной компании требует подписки; бесплатные пути — Podman Desktop или docker-ce внутри WSL2. Выбор инструмента за исполнителем T1.4; контракт один и тот же: тот же Playwright-образ.

**Ось 2 — статус гейта: двухфазный.**

- **До v1.0 (итерации 0–8):** visual-чек в PR выполняется, диф-артефакты прикладываются, но **advisory** — не блокирует merge (continue-on-error + отдельный check-результат, чтобы не приучать «игнорировать красное»: обязательные гейты остаются зелёными отдельно).
- **С «заморозки» компонентного набора (Iteration 10, перед v1.0):** гейт становится **mandatory с ревью диффов**. Осознанное изменение = прогон `test:docker --update-snapshots` + диф в PR.

## Последствия

**Плюсы:** фрикшен обновления эталонов минимальный (локальный контейнер, обычный коммит); нет церемоний бота/path-защиты в рутине; меньше конфликтов (обновления идут коммитами разработчика); блокирующая защита включается тогда, когда её ценность максимальна — после стабилизации компонентного набора, а не в период массовых осознанных изменений.

**Цена/минусы:** контейнер — новое требование к рабочим машинам (закрыто fallback-джобой); advisory-период допускает незамеченные визуальные сдвиги (компенсация: ручной design-QA в релизном чек-листе, axe/e2e продолжают блокировать всегда); смена версии Playwright = смена образа = перегенерация всех эталонов (фиксируется в upgrade-чек-листе).

## Проверка

- T1.4: контрольный компонент — эталон, созданный `test:docker` локально, бинарно совпадает с CI-эталоном;
- T1.5: advisory-чек виден в PR отдельным результатом и не блокирует; джоба `update-snapshots` работает;
- Iteration 10: включение mandatory перед v1.0 отражено в релизном чек-листе (T12.1).
