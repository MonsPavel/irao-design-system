# ADR-0001: Политика фокуса — специфичность «элемент + псевдокласс»

- **Дата:** 2026-10-05
- **Статус:** принято
- **Влияет на:** [02-architecture.md](../02-architecture.md) §1, §5; задачи T1.2, T3.2, T11.1

## Контекст

UI-система подключается в каскаде **первой** (до CSS сайта). На legacy-сайтах регулярно встречаются tag-правила вида `a { outline: none }` (специфичность 0-0-1), подключённые позже. Исходный вариант политики фокуса — `:where(a, button, …):focus-visible { … }` — даёт нулевую специфичность и проигрывает таким правилам по порядку каскада: видимый фокус пропадает на целых страницах. Keyboard-доступность — P0-требование, поломка массовая и незаметная для мышиных пользователей.

## Решение

Политика фокуса в `base/focus.css` записывается списком селекторов «элемент + псевдокласс»:

```css
a:focus-visible,
button:focus-visible,
input:focus-visible,
select:focus-visible,
textarea:focus-visible,
summary:focus-visible,
[tabindex]:focus-visible {
  outline: var(--ui-focus-width) solid var(--ui-focus-color);
  outline-offset: var(--ui-focus-offset);
}
```

Специфичность каждой декларации 0-1-1 — побеждает legacy tag-правила независимо от порядка подключения. Это сознательное исключение из правила «стилизуем только классы»; компоненты по-прежнему стилизуют фокус своими классами — данное правило задаёт гарантированный глобальный минимум. `outline: none` без замены запрещён (stylelint).

## Последствия

**Плюсы:** фокус гарантированно виден даже на страницах с агрессивным legacy-CSS; правило не требует знания о конкретном сайте.

**Цена/минусы:** при появлении нового интерактивного тега список нужно расширять (ответственность задачи T3.2); исключение из односелекторной философии — задокументировано здесь.

## Проверка

E2E-сценарий «legacy-атака» в T3.2: после подключения ui-core инжектится `a { outline: none }`, тест утверждает, что computed `outline-width` в фокусе ≥ 2px. Расширенная версия той же атаки на ключевых компонентах — в T11.1.
