# ADR-0007: Версионирование — semver, поддержка N−1, major в отдельной папке

- **Дата:** 2026-10-05
- **Статус:** принято (фиксирует решение из 02-architecture §11)
- **Влияет на:** T12.1, T12.2, T11.4

## Context

Несколько Bitrix-сайтов будут потреблять систему с разной скоростью миграции. API компонентов — копируемые HTML-паттерны и имена классов: интеграторы не смогут «пересобрать» разметку так же дёшево, как код. Требуется политика, при которой сайты на 1.x и 2.x живут одновременно, а обновление — предсказуемый акт.

## Decision

Строгий semver: PATCH — невидимые фиксы; MINOR — новые компоненты/модификаторы/токены (обратная совместимость); MAJOR — удаление/переименование классов, токенов, data-атрибутов, изменение канонического HTML. Одновременно поддерживаются текущая мажорная и предыдущая (N−1): багфиксы портируются 6 месяцев после выхода N. Major-версии живут на сайтах в отдельных папках. Deprecation: пометка в minor → алиас (dev-сборка пишет warning в консоль) → удаление в major с migration-guide. Релизы: тег → CI-матрица → dist-zip → GitHub Release + CHANGELOG (Keep a Changelog); CI блокирует релиз без changelog-записи.

## Alternatives considered

- **CalVer** — не отражает breaking-изменения, бесполезен для API-контракта.
- **Semver «мягко», с тихими breaking** — ломает прод сайтов, где разметку копировали.
- **Единая «latest»-версия для всех сайтов** — требует синхронного обновления всех потребителей, нереалистично.

## Why

Semver точно кодирует контракт (классы/HTML/токены = API); N−1 + отдельные папки дают сайтам свободу темпа; deprecation-цикл делает мажоры предсказуемыми.

## Consequences

**Плюсы:** параллельные версии на сайтах, предсказуемые обновления, дешёвый откат.
**Минусы/цена:** правило «изменение канонического HTML = major» дисциплинирует разработку системы (любое изменение паттерна — через новый модификатор); поддержка N−1 — регулярные cherry-pick.
