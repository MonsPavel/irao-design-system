# EPIC-17 — Полнота ДС: карьерный портал из компонентов

## Goal

Довести дизайн-систему до состояния, при котором клон career-portal
собирается из компонентов/канонов ДС **почти целиком**: повторяющиеся
сущности, сегодня живущие в сайт-зоне пилота (`pilot.css`, 2022 строки,
228 `cp-*`-селекторов, ~46 блоков; `pilot.js`, 243 строки), переезжают в
ДС — компонентами, паттерн-слоем или токенами. Скрипт сборки клона
(`build.mjs`) при этом остаётся тонким генератором разметки над готовыми
блоками: правки вида «добавить блок» не должны требовать правок CSS/JS
за пределами ДС.

Количественная цель: `pilot.css` ≤ 600 строк только ритма/раскладок
конкретных страниц (сейчас 2022), `cp-*`-блоки ≤ 18 (сейчас ~46),
кар Carousel/галерея-поведение — в `dist/ui.min.js` (сейчас в пилоте).

## Context

Заведён по прямой команде владельца (25.10): «у нас уже есть скрипт,
который создаёт копию карьерного сайта в дизайн-системе, но цель — чтоб
мы НЕ правили скрипт создания клона, а чтоб все стили и компоненты
максимально лежали в дизайн-системе… дизайн-система должна быть настолько
полная, чтоб почти полностью из её компонентов можно было составить
карьерный портал». Это смена критерия полноты: прежнее правило «новый
блок — по мере появления второго потребителя» (PLAN §P2, EPIC-14–16)
заменяется критерием «первый потребитель = career-portal, блок типовой
для сайтов группы → живёт в ДС».

**Раунд 5 (25.10) — регрессионная проверка перед эпиком** (полный разбор —
[REPORT §11](../../../../pilot/career-portal/REPORT.md)): пересборка ДС
на a0e0d21 + пересборка пилота + свежий compare (20 страниц × 2 версии,
2026-10-25T09:32:45Z, 477 ссылок 0 DEAD). Вердикт — **новых регрессий
нет**: все 127 расхождений проб классифицированы как документированные
«принято ДС» (прозрачная рамка кнопок +4px, AA gray-700, паддинги 24),
ASYM-артефакты выборки (скрытые модалки, разные сущности под первым
вхождением), контент-различия упрощённых данных и осознанная замена
a0e0d21 (заголовки карточек media/career-track → h2, решение T15.9).
Отдельно зафиксирован мелкий сайт-зонный дифф раунда: колонка сайдбара
вакансий 280px (оригинал) против 320px (пилот) — растягивает промо-кнопку
(238→270px при одинаковом тексте 125.23px и паддингах) — калибруется в
каноне list-page (задача строк/сайдбара).

**Ценз сайт-зоны (источник задач).** 46 `cp-*`-блоков по судьбе:

1. **Канон в ДС уже есть — пилот дублирует (~10 блоков)**: строка
   вакансии и сайдбар (канон `lpp-row`/`lpp-side` T14.10, дрейф чинил
   T16.5), таймлайн (паттерн T14.11 — пилот на собственной копии),
   page-head и ритм крошек (каноны list/detail/form-page), каркасы
   шапки/подвала (паттерны T7.6), композиция детальной страницы
   (detail-page), find-bar (вакуансии + поиск мероприятий). Дублирование
   существует потому, что паттерны ДС — доки без кода в dist
   (02-architecture §7): связки копируются руками и дрейфуют.
2. **Повторяющиеся сущности без аналога в ДС (~16 блоков)**: фото-секции
   (hero, production, holding, why-us, company-banner — один приём
   «фон inset:0 + оверлей» пять раз), статы (holding, company — три
   варианта заливки), медиа-карточка (event/article/intern-person — фото
   + тег на фото + тело), пилюля select-фильтра (`cp-pill`, 4 контекста),
   CTA-карточки (cta-mail, «Все вакансии»), цветные nav-карточки
   (students), лента логотипов (employers), видео-плеер, карусель со
   степпером (production), фото-галерея prev/next (направления),
   типографская marquee-полоса (T16.15), спец-тинты hero-тегов.
3. **Контент-композиции конкретных страниц (~14 блоков) — остаются
   сайт-зоной по архитектуре**: article-meta/type/gallery, dir-modal,
   cover-hero, спец-сетка media (big+lead), ленты каталог-фильтров,
   центрирование пагинации ×2, бренд-строки шапки/футера (hover-accent,
   VI-пилюля 15px), лестницы max-width 1023/767.

Распределение строк по блокам (топ): hero 17 селекторов, production 17,
footer 14, header 11, why-us 10, students 10, holding 9, vacancy-page 8,
adv-marquee 8, vac-row 6, event-card 6.

## Ключевое решение — ПРИНЯТ вариант A (владелец, 25.10)

Паттерны ДС сегодня — доки без кода (`patterns/` → «нельзя: новый
CSS/JS», 02-architecture §7). Копипаста канона в пилоте уже дрейфовала
(строка 16px против канона 24/28 — T16.5). Были два варианта:

- **A (ПРИНЯТ): паттерн-слой `dist/ui-patterns.css`.** Канонические
  связки (`lpp-*`, `ddp-*`, `fpp-*`, каркасы шапки/подвала, find-bar)
  поставляются опциональным CSS-файлом — сайты подключают по желанию,
  `ui-core.min.css` не раздувается. Паттерны-доки продолжают ссылаться
  на те же классы (один источник правды). Прямо отвечает цели «всё лежит
  в ДС»; пилот переключается на `lpp-*`-классы и снимает дубликаты.
- B (отклонён): копипаста + машинный гейт «связки пилота == канон
  паттерна» — дешевле по dist, но каждый новый сайт группы повторяет
  копипасту и риск дрейфа.

## Risks

- **Раздувание dist**: паттерн-слой добавляет CSS-объём — митигируется
  опциональностью подключения (отдельный файл, не ui-core) и запретом
  дублирования компонентов в слое (слой — только связки, которых нет в
  ядре);
- **Каша «компонент vs паттерн»**: граница зафиксирована правилом —
  повторяемая визуальная сущность с собственными состояниями = компонент
  (ui-stat, ui-card--media, ui-carousel); композиция из компонентов =
  паттерн/слой (hero, find-bar, шапка). Спорные случаи — решение
  владельца в задаче;
- **Регрессии пилота при переключении классов**: adoption идёт блоками с
  probe-контролем после каждого (прецедент T16.5); ladder'ы 1023/767
  переезжающих блоков конвертируются в mobile-first ступени ДС — риск
  пропуска ступени, митигируется визуальным прогоном 375/768/1280/1440;
- **Вторые потребители**: сущности эпика проектируются по одному
  потребителю — README каждого компонента обязан описать параметры
  (токены-хуки), которыми сайт группы кастомизирует вид без fork'а
  (уроки ui-tag--filter T16.14).
