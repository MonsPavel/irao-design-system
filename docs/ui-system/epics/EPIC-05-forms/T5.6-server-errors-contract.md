## Goal

Ошибки после сабмита (перезагрузка страницы, рендер PHP) выглядят и ведут себя идентично клиентским; контракт задокументирован сниппетами для `bitrix:form.result.new`; интеграционный стенд «форма целиком» закрывает MVP-код.

## Context

Сценарий реального сайта: Bitrix-форма валидирует на сервере и перезагружает страницу с сообщениями. Если серверный рендер отличается от клиентского — пользователь видит два разных интерфейса ошибок. Система обязана снять это контрактом: PHP рендерит те же классы и aria.

## Scope

- контракт (дока): для поля с ошибкой PHP выводит `ui-field--error` + `aria-invalid="true"` + `aria-describedby="…-err"` + `<p class="ui-field__error" id="…-err">`; сводная — `ui-form__summary[role=alert]`; фокус-менеджмент: при наличии ошибок фокус на summary (inline-скрипт-сниппет);
- сниппеты `bitrix/snippets/form-error-render.php` — шаблон вывода ошибок `bitrix:form.result.new` (маппинг FIELD_NAME → html);
- интеграционный стенд «форма целиком»: без JS (нативная валидация) → с JS (блокировка+фокус) → «серверный ответ» (pre-rendered ошибки) → success; стенд эмулирует PHP статикой;
- правило: серверная валидация всегда включена (JS — только UX) — в доку.

## Out of scope

- Реальная обработка на стороне Bitrix (зона сайта);
- AJAX-отправка (появится на сайтах — контракт тот же, отметить в доке).

## Existing implementation

career-portal: серверной части нет (мок); клиентские классы ошибок — основа контракта.

## Implementation requirements

1. Сниппет-шаблон с циклом по `$arResult["FORM_ERRORS"]` (или массиву ошибок произвольной формы) — копипаст-готовый.
2. Стенд покрывает все четыре ветки; каждая ветка — отдельный якорь-состояние для e2e и visual.
3. Фокус-менеджмент серверного состояния: inline `<script>`-сниппет (работает без модулей) — в bitrix-сниппеты.

## Technical considerations

- Контракт стабильнее классов: изменение классов ошибок = major (ADR-0007);
- стенд живёт в showcase как «integration/form-full-cycle».
