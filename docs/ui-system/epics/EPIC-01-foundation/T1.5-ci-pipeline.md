# TASK T1.5 — CI-конвейер с mandatory-гейтами

## Epic

[EPIC-1 — Foundation & Tooling](README.md)

## Priority

P0

## Type

TASK

## Goal

PR не мёржится без полного набора проверок; showcase и dist-артефакт публикуются автоматически; visual-гейт работает в advisory-режиме до v1.0 (ADR-0004).

## Context

GitHub Actions (решение Phase 0). Схема гейтов утверждена 02-architecture §10 и 06 §7: mandatory — lint, html-validate, unit, build, e2e+axe, контраст-скрипт (подключится в T2.3); visual — advisory (continue-on-error, отдельный check-результат, диф-артефакты прикладываются); матрица браузеров и scaling/VI-smoke — nightly/release.

## Scope

- `ci.yml` (PR): lint → html-validate → unit → build → e2e+axe+visual в контейнере Playwright-образа (visual advisory);
- джоба `update-snapshots` (workflow_dispatch, коммит бота) — fallback ADR-0004;
- `pages.yml` (main): деплой showcase на GitHub Pages;
- `release.yml` (тег): каркас — матрица + артефакты (боевой режим в T12.1);
- nightly: матрица chromium/firefox/webkit;
- branch protection: обязательные проверки lint/build/unit/e2e.

## Out of scope

- Контраст-скрипт (добавится в T2.3 как шаг);
- релизные матрицы в полном объёме (T12.1);
- GitLab-зеркало (нет решения Phase 0).

## Existing implementation

career-portal `.github/workflows/deploy.yml` (GitHub Pages deploy, Python) — используем как референс структуры, но стек другой (Node/esbuild).

## Implementation requirements

1. Advisory-visual реализовать отдельным step'ом с `continue-on-error: true` и именованным check-результатом — обязательные гейты должны оставаться зелёными независимо от visual.
2. Кэш npm + кэш Playwright-браузеров для скорости.
3. Артефакты PR: dist-zip + visual-дифы (даже advisory).
4. Включить branch protection после первого зелёного прогона (нужны права администратора — зафиксировать в отчёте задачи, если недоступно).

## Technical considerations

- Job-контейнер: `container: mcr.microsoft.com/playwright:vX-jammy` — тот же образ, что локально (ADR-0004);
- Pages-деплой из `main` только после зелёного CI.

## Acceptance Criteria

**Локально-проверяемая часть (конвейерная приёмка):**

- [x] Воркфлоу существуют и структурно соответствуют архитектуре: `ci.yml` (lint → html-validate → unit → build → e2e+axe → visual advisory, ADR-0004), `pages.yml`, `release.yml` (каркас), `update-snapshots.yml` (fallback-джоба), `nightly.yml` дополнен шагами lint/unit/contrast; состав гейтов и advisory/mandatory-разделение соответствуют 06 §7; валидация — `tools/validate-workflows.mjs` (локальный структурный валидатор, T1.5);
- [x] Демо-ветка для красного PR подготовлена (`task/T1.5-demo-red`, запушена).

**Живая часть — чек-лист владельца (исполняется на живом GitHub ПОСЛЕ мержа; агентам конвейера недоступна по полномочиям):**

- [ ] Демо-PR с нарушением (из `task/T1.5-demo-red`) блокируется обязательными гейтами;
- [ ] Чистый PR зелёный ≤ 5 минут;
- [ ] Visual-падение не блокирует merge, но отражается отдельным check-результатом с приложенными дифами;
- [ ] После merge в main showcase обновляется на Pages;
- [ ] Джоба `update-snapshots` запускается вручную и коммитит эталоны от бота;
- [ ] Эталон, созданный локально через `npm run test:docker`, бинарно совпадает с эталоном, созданным джобой CI (контрольный компонент) — перенесено из T1.4, решение 06.10.

> **Изменение 06.10 (после форс-запуска):** конвейерная приёмка честно заблокировала задачу — все AC требуют живого GitHub (открытие PR, наблюдение Actions, merge, dispatch), что вне полномочий агентов (реализатору запрещено мерджить/пушить вне ветки — дисциплина корректна). Разделение: структурная часть подтверждается приёмкой, живой чек-лист исполняет владелец после мержа (первый реальный прогон Actions дополнительно валидирует синтаксис воркфлоу).
